# 基于 Haystack fork 开发，并逐项评估增量效果

用户确认以 Haystack 上游仓库的 fork 为开发基础，优先使用组件与 Pipeline 扩展接口，仅在接口不足时考虑修改框架核心。评测基线为最小 Haystack 应用；Qdrant、BM25 和后续业务改进分别测量增量效果，旧 Trust RAG 不作为效果对比基线。

最终实现保留表格精确查询与答案校验。先运行 baseline 并分析失败案例，再确定进一步优化方向，不预设效果提升。

## 已确认的实验顺序

| 阶段 | 配置变化 | 评估目的 |
|---|---|---|
| B0 | Haystack InMemoryDocumentStore + InMemoryEmbeddingRetriever + 固定生成模型 | 最小纯向量检索基线 |
| B1 | 将向量存储与检索后端替换为 Qdrant | 后端变化的质量、延迟与资源影响 |
| B2 | 增加 BM25 与结果融合 | 混合检索的增量效果 |
| B3 | 增加表格精确查询 | 结构化取数的增量效果 |
| B4 | 增加答案校验 | 正确率、拒答率与开销变化 |

所有阶段使用同一批现有文档和现有 298 题，文档来源、评测问题、embedding 和生成配置保持一致。表格从 B0 起以普通文本形式参与检索，B3 再增加结构化精确查询；分别报告条款题与表格题结果。该决定替代此前仅对条款向量化的初步范围，避免将新增数据覆盖误算为精确查询收益。最终通过关闭单个组件补充消融验证，不将累积增益直接视为组件的独立收益，也不预设 Qdrant 会提高正确率。

embedding 与生成模型均调用外部 API，固定具体模型与配置并记录调用成本。用户接受生成模型优先沿用已有服务、embedding 优先选择同服务中文检索模型的方向；先进行开发集小样本兼容性验证与全量费用估算，再冻结配置。具体服务和模型仍需核实，不能将方向确认解释为具体模型已确定。

## 资源约束

用户明确允许 baseline 超过 2 GiB，最终成品部署在 Linux 裸机上，整机 2 GiB 物理内存加 2 GiB swap，以减少容器部署成本。内存预算覆盖操作系统、后台服务、应用、Qdrant 与其他本地组件，导入和查询均需满足；不能将全部 2 GiB 分配给应用。用户明确允许使用 swap，因此不能将该要求解释为物理内存与 swap 总和不超过 2 GiB；验收需分别记录物理内存、swap 用量与延迟。验收机器已核实，实际整机验收仍待完成。分别记录各阶段的实际内存消耗与资源限额，效果对比不因 baseline 超限而单独缩小其语料。

首轮验收双并发问答，导入与查询分时运行，导入在维护时段执行。分别记录检索与完整问答的 P50/P95 延迟。

## 数据划分与最终组件选择

用户确认将现有 298 题按类别分层划分，约 70% 开发集、30% 保留测试集，并要求每类题目在两集合中都有覆盖。关联同一证据的题目尽量放在同组；划分前需审计真实类别分布及分组可行性，不通过复制同题到两集合来满足覆盖要求。旧项目可能已使用过这些题，不能将该保留集称为全新盲测。各阶段使用固定划分。

用户确认最终成品可移除成本增加而收益不足的组件，同时保留相应实验结果。以正确率不低于 baseline 为质量目标，报告拒答、错误作答与引用依据；如未达到，必须如实报告，不能将迁移完成当作效果提升。

首轮使用现有标注，不额外要求补标引用原文。298 题均有标准答案，其中 98 题带页码、工作表或单元格定位，暂无引用原文 gold。首轮报告答案正确率、拒答率、文档来源命中率和适用题目的定位命中率；引用忠实性仅作抽样检查，不宣称有完整细粒度 Recall@k 或引用忠实性真值。B4 不能以在线 Verifier 自评通过率代替独立正确性评价。

已核实五类 qa_type：表格取数 34、表格比较 33、表格计算 31、单事实检索 134、多事实检索 66。五类均有多个证据组，初步具备两集合覆盖的条件；正式划分还需检查别名、重复与近重复问题。分组与覆盖优先于严格的 70/30 比例，并报告来源、难度交叉覆盖矩阵。
