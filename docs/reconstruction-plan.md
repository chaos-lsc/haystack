# Trust RAG 重构与增量评测方案

状态：用户已确认进入实现。本地已检出 Haystack v3.1.1，已创建 chaos-lsc/haystack fork；应用评测进行中，真实 Linux 资源验收尚未完成。

## 目标与开发边界

基于 deepset-ai/haystack 的 GitHub fork 开发新的 Trust RAG 应用。优先通过 Haystack 组件与 Pipeline 扩展，只有扩展接口不足时才修改框架核心。旧项目作为语料、业务逻辑和评测资产来源，不作为效果 baseline；不继承其大量未提交应用改动作为新项目起点。

最终交付包括可运行问答服务、裸机启动和维护说明、可重建的索引流程、固定评测集划分、逐题结果、阶段比较与消融报告。首轮范围围绕现有 298 道选择题问答及相应检索、表格取数/比较/计算和答案校验；现有前端的完整移植未列入已确认范围。

## 实验矩阵

| 阶段 | 唯一主要变化 | 比较对象 |
|---|---|---|
| B0 | Haystack 内存文档存储、内置纯向量检索、固定 API 生成 | 基线 |
| B1 | 替换为 Qdrant 向量存储与检索 | B0 |
| B2 | 加入中文 BM25 检索及结果融合 | B1，同时报告相对 B0 |
| B3 | 加入表格精确查询能力 | B2，同时报告相对 B0 |
| B4 | 加入答案校验 | B3，同时报告相对 B0 |

最终候选分别关闭可独立开关的组件，检查其条件贡献；不把顺序累积的收益解释为组件独立收益。最终可移除收益不足的组件，但保留该阶段结果。若开发集暴露需要其他优化，先明确单项实验假设再实施。

同一批条款和表格从 B0 起均可检索，表格使用固定文本表示。表格精确索引在 B3 启用，不能通过只给后期阶段增加语料来形成虚假提升。B3 的范围包含现有评测所需的取数、比较和计算，具体逻辑需对照旧项目审计后复用。

## 数据与模型冻结

- 使用现有文档和 298 题，保存来源版本、文件哈希、证据 ID、预处理配置和评测题目哈希。
- 各阶段使用同一文本切分、表格文本表示、embedding 模型及维度、生成模型、基础提示词和预算；校验阶段的额外调用单独记录。模型远程版本不可锁定时，记录时间与服务返回的模型标识。
- embedding 与生成均走外部 API。优先核实已有服务，再做小样本兼容性检查和全量费用估算；缓存以文本哈希及完整模型配置为键，避免阶段间重复付费建库。
- 使用流式读取、分批入库、可恢复进度与磁盘缓存。禁止把全部 JSONL、向量和 BM25 对象同时载入最终服务。
- 题目答案、预期证据位置与分类标签仅供离线划分/评测，不得写入检索语料、提示词或在线路由。

## 分组划分

五种 qa_type 必须同时覆盖开发集和测试集：表格取数 34、表格比较 33、表格计算 31、单事实检索 134、多事实检索 66。

先归一证据来源别名并检查重复/近重复问题，再按关联证据归组，寻找接近 70/30 的分层划分。覆盖与防止泄漏优先于精确比例；不得复制同一道题跨集合。报告 qa_type、source_type、difficulty 及其交叉覆盖。现有 PDF 文档组较少，不强求每个交叉层均为 70/30。

开发集用于诊断、调参及组件选择。冻结实现、配置和组件选择后，统一运行各阶段保留测试集并出报告；不能根据测试集结果继续挑选最佳组件并仍宣称为未见测试。若重新调优，记录测试集已被使用。旧项目使用过的题目不称为全新盲测。

## 效果与性能报告

主指标为正确题数除以固定评测题数；拒答和运行错误不能从分母中移除。分别报告五类、来源与难度表现，并逐题对齐阶段间由错变对、由对变错、拒答和错误状态。

辅助指标为文档来源命中率、具备位置标注题目的定位命中率、错误作答率、拒答率、检索与端到端 P50/P95、API 次数与费用、建库耗时、磁盘占用、物理内存及 swap 峰值。没有细粒度证据 gold 的题目不报告伪精确引用召回率；引用忠实性仅做明确样本范围的检查。

记录超时、重试、缓存和冷/热状态，保持比较协议一致；失败不得无记录地重跑到成功。B4 使用标准答案而不是自身校验通过率证明效果。

质量目标为最终正确率不低于 B0。当前未约定硬延迟 SLA 或必须提高的百分点，必须如实报告退步与成本。小样本差异不能直接宣称统计显著。

## 裸机资源验收

最终目标为 Linux 整机 2 GiB 物理内存加 2 GiB swap，不采用容器作为交付前提。双并发问答；导入在维护时段运行，与查询分时。应用、Qdrant、操作系统与后台进程共同占用这台机器的资源。

验收覆盖完整导入、索引优化、冷启动及持续双并发查询，检查 OOM、服务错误、系统可用内存、进程 RSS、swap 用量/换页与延迟。应记录 CPU、磁盘、内核、Python、Haystack 和 Qdrant 版本以及负载持续时间。

baseline 仅在本地用于对比，不部署到远端。质量对比保持相同数据与模型；跨硬件的延迟和资源数字须标注环境，不直接归因于组件。在本地比较各阶段性能后，远端只部署选出的最终改进版，并在目标小内存机器验收最终成品。

Qdrant 的向量、索引及 payload 磁盘存储策略按固定版本验证；开启磁盘存储不等于没有内存占用，后台索引优化也要测量。BM25 需明确中文分词与实际算法实现，不能将任意 sparse embedding 检索称为 BM25。

## 执行顺序与完成证据

1. 核实 GitHub 登录及目标账号，fork Haystack，记录上游提交并建立开发分支；保留本目录设计文档。
2. 审计可复用数据与业务逻辑，生成语料清单、覆盖矩阵和固定划分；核实 API 并估算费用。
3. 完成 B0，在开发集跑通并保存逐题结果、资源与成本基线。
4. 依次实施 B1–B4，每个阶段只在开发集诊断与调参，形成可开关配置与比较结果。
5. 使用开发集完成组件选择与消融，冻结最终候选；运行各阶段保留测试集，输出统一报告。
6. 在目标 Linux 机器执行资源验收，提交部署说明、运行记录与最终结论。

真实 Linux 验收未完成时，只能报告实现完成或本地验证完成，不能报告整机 2 GiB 验收通过。
